====================================================
FRAUDGUARD — DAY 2 TECHNICAL EXPLANATION
Topic: Auth Service — JWT, Bcrypt, and Microservices Security
====================================================

Congratulations on completing Day 2! Today we built the foundation of security for the entire FraudGuard ecosystem. In a JP Morgan or Tier-1 Fintech interview, security and architecture are the two most important topics.

Below is the "Interview Cheat Sheet" for everything we built today.

----------------------------------------------------
1. THE ARCHITECTURE: WHY A SEPARATE AUTH SERVICE?
----------------------------------------------------
In a monolith, auth is just a middleware. In microservices, it's a standalone service.
- Why? So other services (Transaction, Scoring) don't need to manage users.
- Independent Scaling: If thousands of users try to login at once, we only scale the Auth Service container.
- Separation of Concerns: Auth Service owns the 'users' collection. No other service can touch it.

----------------------------------------------------
2. THE DATABASE: LOGICAL SEPARATION
----------------------------------------------------
We used MongoDB Atlas with a 'users' collection.
- Question: "Why one DB for 4 services?"
- Answer: "For development efficiency and cost, I used one cluster. But in code, I enforced 'Logical Separation' — the Auth Service is the only one with the User model. Transaction Service will never talk to the users collection directly."

----------------------------------------------------
3. SECURITY: BCRYPTJS & PASSWORD HASHING
----------------------------------------------------
We NEVER store plain text passwords. We used `bcryptjs`.
- How it works:
  1. Generate a 'Salt' (random data).
  2. Combine Salt + Password.
  3. Hash it (one-way function).
- Pre-save Hook: In `User.js`, we used `userSchema.pre('save')`. This ensures that every time a user is created or their password changes, it's automatically hashed before hitting the DB.

----------------------------------------------------
4. AUTHENTICATION: JWT (JSON WEB TOKENS)
----------------------------------------------------
We used JWT for stateless authentication.
- Why JWT? In microservices, the server doesn't keep sessions (no `req.session`).
- The Flow:
  1. User logs in.
  2. Auth Service signs a token with their `userId`.
  3. User sends this token in the `Authorization: Bearer <token>` header for every request.
  4. Other services verify this token using the SAME `JWT_SECRET`.
- Verification: The `authMiddleware.js` extracts the token, verifies it, and attaches the user to `req.user`.

----------------------------------------------------
5. THE CODE STRUCTURE (FOLDER BY FOLDER)
----------------------------------------------------
- src/config/db.js: Centralized database connection logic.
- src/models/User.js: Defined the data structure. Used `select: false` on password so it's not accidentally sent in API responses.
- src/controllers/authController.js: The "Brain". Handles logic for Register, Login, and Me.
- src/middleware/authMiddleware.js: The "Gatekeeper". Protects routes from unauthenticated users.
- src/routes/authRoutes.js: Defined the entry points (URLs).

----------------------------------------------------
6. INTERVIEW Q&A (PRACTICE THESE!)
----------------------------------------------------

Q: "What is the difference between Authentication and Authorization?"
A: "Authentication is WHO you are (Login/JWT). Authorization is WHAT you can do (Roles like Admin vs Analyst)."

Q: "Why did you use a separate Salt for bcrypt?"
A: "Salt prevents 'Rainbow Table' attacks. Even if two users have the same password, their hashes will be different because their salts are different."

Q: "How do other services know if a user is logged in?"
A: "They use the same JWT_SECRET to verify the token. This is the beauty of JWT — it allows 'Shared Secret' verification across services without them needing to talk to each other for every request."
