----------------------------------------------------
2. ARCHITECTURAL DECISIONS (INTERVIEW Q&A)
----------------------------------------------------

QUESTION: "How did you handle data visualization in your microservices architecture?"
ANSWER: 
"I used Recharts, a D3-based React library, to build responsive, data-dense charts. To fetch the data, I implemented specialized aggregation endpoints in the Transaction Service. Instead of fetching thousands of raw transactions and processing them on the frontend (which would be slow and consume excessive memory), I leveraged MongoDB's Aggregation Framework to perform the heavy lifting on the server side. This ensures the frontend only receives the summarized data it needs to render the charts."

QUESTION: "Tell me about the MongoDB Aggregation Pipeline you used for trends."
ANSWER:
"For the 7-day trend chart, I used a multi-stage pipeline:
1. $match: Filters transactions from the last 7 days that are flagged as suspicious or fraudulent.
2. $group: Uses $dateToString with format '%Y-%m-%d' to group records by calendar day.
3. $sort: Orders the results chronologically.
This approach reduces network overhead and ensures the frontend stays responsive even with millions of records in the database."

QUESTION: "Why did you choose Recharts over other libraries like Chart.js or D3 directly?"
ANSWER:
"Recharts is built specifically for React. It uses declarative components, which aligns perfectly with the React paradigm. While D3 gives absolute control, it has a steeper learning curve and can be overkill for standard business dashboards. Recharts provides the right balance of customization (like gradients and animations) and development speed, which is critical in a fast-paced fintech environment."

QUESTION: "How do you ensure the dashboard shows 'live' data in a microservices setup?"
ANSWER:
"I implemented an auto-refresh mechanism using React's useEffect and setInterval, which polls the backend every 30 seconds. This is a common pattern for monitoring dashboards where near-real-time updates are sufficient. In a production scenario with higher frequency requirements, I would transition to WebSockets (using Socket.io) or AWS AppSync for real-time push notifications from the Transaction and AI Scoring services."

3. TECHNICAL IMPLEMENTATION DEPTH
----------------------------------------------------

A. DATA AGGREGATION PATTERN:
We follow the 'Backend-for-Frontend' (BFF) philosophy by creating specific endpoints (/stats, /trends, /categories) that return exactly what the UI needs. This prevents 'over-fetching' and improves page load times.

B. VISUAL EXCELLENCE:
- Area Charts: Used for 'Trends' to provide a sense of volume and continuity.
- Bar Charts: Used for 'Hourly' data to quickly identify spikes in fraudulent activity (e.g., midnight attacks).
- Pie Charts: Used for 'Category' to show where the system is losing the most money.

C. THE 'PREMIUM' FEEL:
- CSS Transitions: Added 'animate-in' for smooth entry.
- Hover Effects: Cards scale and borders glow when hovered.
- Dark Mode Palette: Used a Bloomberg-inspired navy/black theme (#0F1117) to signal high-stakes financial security.

6. CORE CONCEPT: DATABASE SEEDING
----------------------------------------------------

QUESTION: "What is Database Seeding and why is it important?"
ANSWER:
"Seeding is the process of populating a database with an initial set of data. In our microservices architecture, we use it to create 'Seed Users' (Admin/Analyst) so the system is usable immediately after deployment. It's critical for:
1. Automated Testing: Ensuring tests run against a known data state.
2. Development Speed: New team members don't have to manually create data.
3. Version Control: We track our data schema changes and initial state in the repository."

QUESTION: "Why did you run the seeding script from the service folder instead of the root?"
ANSWER:
"This is a monorepo structure. Each microservice has its own node_modules. To ensure that dependencies like 'dotenv' and our 'User' model are correctly resolved, the script must be executed within the service's context. This demonstrates an understanding of Node.js module resolution and monorepo management."

8. REAL-WORLD TROUBLESHOOTING (INTERVIEW GOLD)
----------------------------------------------------
During the development of the Day 13 dashboard, we encountered several "production-level" hurdles. Being able to explain how you solved these will set you apart from other candidates.

ISSUE 1: "EADDRINUSE: address already in use :::3001"
- Scenario: The server fails to start because the port is already taken.
- Technical Fix: Use `netstat` to find the process ID (PID) and `taskkill` (Windows) or `kill -9` (Linux) to free the port.
- Interview Tip: "This happens when a previous instance of the server didn't shut down correctly. I handle this by identifying the zombie process and forcefully terminating it, ensuring a clean start for the new deployment."

ISSUE 2: "Mongoose: Operation buffering timed out"
- Scenario: The application hangs while trying to reach the database.
- Technical Fix: This is almost always a network/security issue. In MongoDB Atlas, you must whitelist the IP address (Add 0.0.0.0/0 for global dev access).
- Interview Tip: "I debugged this as a connectivity issue rather than a code bug. I verified that the Atlas Network Access rules were blocking the connection and updated the firewall settings to allow the microservice to communicate with the cluster."

ISSUE 3: "Cannot find module 'dotenv/config' (Transitive Dependencies)"
- Scenario: A script runs fine in one folder but fails in another.
- Technical Fix: In a monorepo, each service has its own `node_modules`. Running scripts from the root often fails because paths aren't resolved.
- Interview Tip: "I solved this by correctly scoping the execution context. Instead of running a global command, I navigated into the specific microservice folder to ensure all local dependencies were correctly linked and loaded."

ISSUE 4: "Recharts: width(-1) and height(-1) warnings"
- Scenario: Charts appear blank or show console errors in a CSS Grid.
- Technical Fix: CSS Grid sometimes fails to provide an initial width to child elements. Adding `min-w-0` to the grid containers allows the charts to calculate their dimensions correctly.
- Interview Tip: "I identified a conflict between the flex/grid layout and the ResponsiveContainer component. I resolved it by ensuring the parent container had a defined minimum width, allowing the SVG-based charts to render accurately."
