DAY 18: TRANSACTION FEED, FILTERING LOGIC & SERVICE ABSTRACTION
==============================================================

OVERVIEW
--------
Day 18 focused on the core monitoring interface: the Live Transaction Feed. This session bridged the gap between the UI components created on Day 17 and the backend services. Key achievements included building a robust filtering system, abstracting API logic into a dedicated service layer, and implementing real-time data orchestration for the main monitoring dashboard.

KEY IMPLEMENTATIONS
-------------------

1. transactionService.js (Service Layer Abstraction)
   - Purpose: Centralize all API interactions related to transactions to maintain the "Don't Repeat Yourself" (DRY) principle.
   - Features:
     - Methods for fetching all transactions with dynamic query parameters.
     - Support for individual transaction lookup, creation, and status updates.
     - Specialized endpoints for dashboard stats, trends, and review queues.
   - Design Pattern: Service Pattern — decouples the React components from the Axios/Network logic, making the codebase easier to test and maintain.

2. Enhanced FilterBar Component (Precision Search)
   - Purpose: Allow fraud analysts to drill down into specific subsets of transaction data.
   - New Capabilities:
     - Search: Multi-field search (ID and Merchant Name).
     - Status/Category: Semantic dropdowns for workflow state and business vertical.
     - Amount Range: Min/Max numerical inputs for identifying high-value anomalies.
     - Date Range: Integrated `react-datepicker` for time-based investigation (e.g., "Show me all transactions from last night").
   - UX: Responsive grid layout that collapses from a 6-column desktop view to a stacked mobile view.

3. TransactionFeed Page (The Command Center)
   - Purpose: The primary workspace for fraud analysts.
   - Data Flow:
     - Implements `useState` for filter management and `useEffect` for automated data fetching.
     - Maps complex UI filter states (like Date objects) to backend-expected formats (ISO strings).
     - Features a "Manual Refresh" and "Simulate Payment" capability for live testing.
   - Error Handling: Integrated `LoadingSkeleton`, `EmptyState`, and `ErrorState` components to handle all network scenarios gracefully.

INTERVIEW PREPARATION GUIDE (Q&A)
---------------------------------

Q1: Why did you create a separate `transactionService.js` instead of calling Axios directly in your components?
A1: This is called the Service Pattern. It provides three main benefits:
    1. Separation of Concerns: The component only cares about *what* data to show, not *how* to get it.
    2. Maintainability: If the API URL or headers change, I only update one file instead of 10 different pages.
    3. Reusability: Multiple components (Dashboard, Feed, Audit Log) can share the same fetching logic.

Q2: How do you handle complex filtering logic where some fields might be empty?
A2: On the frontend, we use a clean object-to-query mapping. In `transactionService`, we build a `URLSearchParams` object and only append a key if a value exists. On the backend, we use MongoDB's dynamic query object—starting with an empty `{}` and adding properties like `{ status }` or `{ amount: { $gte: min } }` only if they are present in the request query.

Q3: Explain the choice of `react-datepicker` for the date range filter.
A3: Date handling is notoriously difficult in JavaScript. `react-datepicker` provides a polished, accessible UI for selecting dates and handles timezone complexities better than a standard `<input type="date">`. For the backend, we convert these objects to ISO strings (`.toISOString()`) to ensure the server receives a standardized, UTC-based timestamp.

Q4: What happens if a user applies filters that return no results?
A4: We implemented an `EmptyState` component. Instead of just showing a blank screen (which might look like a bug), we show a clear illustration with a message: "No transactions found. Try adjusting your filters." This improves the "User Experience" by giving the analyst a clear next step.

Q5: Why did you add a "Reset Filters" button?
A5: In high-speed monitoring environments, analysts often dive deep into a specific filter and need a one-click way to return to the "Global View." Our reset logic clears the local state and immediately triggers a fresh API call with default parameters to ensure the UI remains in sync with the data.
