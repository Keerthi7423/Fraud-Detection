DAY 20: REVIEW QUEUE PAGE & INLINE ACTIONS
==============================================================

OVERVIEW
--------
Day 20 focused on creating an efficient Review Queue interface where analysts can perform inline actions (Approve/Reject) directly from the queue, minimizing context switching and improving operational throughput. The core implementation involved reusing our existing TransactionTable component (with modifications for queue-specific actions), and building an ActionModal component to handle analyst notes and workflow confirmation.

KEY IMPLEMENTATIONS
-------------------

1. ActionModal Component (Contextual Validation)
   - Tech: React, Tailwind CSS, Lucide React
   - Purpose: To capture mandatory analyst review notes during state transitions (Approve/Reject).
   - Design: 
     - Centered modal with dark, glassmorphic overlay (`backdrop-blur-sm`).
     - Dynamic button colors and copy based on the action intent (Green for Approve, Red for Reject).
     - State-driven validation: The "Confirm" button is conditionally disabled unless a valid review note (min 10 chars) is provided, ensuring an audit trail.

2. TransactionTable Component Extension (Reusability)
   - Tech: `@tanstack/react-table`
   - Purpose: Rather than creating a separate table for the Review Queue, I extended the existing `TransactionTable` component.
   - Design: 
     - Introduced an `isQueueView` boolean prop to conditionally render the `Actions` column.
     - When `isQueueView` is true, the table renders inline "Approve" and "Reject" buttons alongside the standard "View Details" button.
     - Passed an `onAction` callback from the parent `ReviewQueue` component to orchestrate state updates and open the modal, keeping the table component decoupled from business logic.

3. ReviewQueue Page (Analyst Workflow Hub)
   - Tech: React, custom `transactionAPI` service, `react-hot-toast`
   - Purpose: To display transactions explicitly requiring human review (high-risk or suspicious statuses).
   - Features:
     - Real-time data fetching on mount with loading skeletons.
     - Empty state handling (`All caught up! No transactions need review.`) for improved UX.
     - Optimistic UI updates / automated refetching post-action to ensure the queue remains current after a transaction is processed.
     - Error handling gracefully displays an actionable retry block if network requests fail.

INTERVIEW PREPARATION GUIDE (Q&A)
---------------------------------

Q1: Why did you extend the existing `TransactionTable` component instead of building a new one for the Review Queue?
A1: Extending existing components promotes DRY (Don't Repeat Yourself) principles and maintains visual consistency. By injecting an `isQueueView` prop, I enabled the table to intelligently adapt its last column (Actions) to provide inline Approve/Reject capabilities without duplicating the core sorting, pagination, and rendering logic provided by TanStack table. This makes future maintenance significantly easier.

Q2: How do you handle UI state during destructive or high-impact actions like Approving/Rejecting a transaction?
A2: I implemented a separation of concerns by utilizing a dedicated `ActionModal` component. When a user clicks "Approve" or "Reject" inline, it doesn't immediately dispatch an API call. Instead, it triggers the modal, enforcing a confirmation step where the user MUST provide a 10-character minimum note. This acts as both a safety buffer against accidental clicks and enforces compliance for our audit trails.

Q3: Can you explain the data flow when an analyst clicks "Approve" in the queue?
A3: 
1. Analyst clicks "Approve" in the `TransactionTable` row.
2. The `onAction` callback fires, passing the `transactionId` and `actionType` up to the `ReviewQueue` parent component.
3. `ReviewQueue` updates its local state (`selectedTxn`, `actionType`) and sets `modalOpen` to true, rendering the `ActionModal`.
4. The analyst enters a note and clicks "Confirm Approve" inside the modal.
5. The `handleConfirmAction` function in `ReviewQueue` issues a `PATCH` request to the backend.
6. Upon success, a toast notification is displayed, the modal closes, and `fetchQueue()` is called again to refresh the list, removing the processed transaction from the queue.
