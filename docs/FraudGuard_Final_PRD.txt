2.1 MICROSERVICES ARCHITECTURE OVERVIEW
----------------------------------------------------

FraudGuard is split into 5 independent microservices.
Each service has its own codebase, its own database,
and is deployed in its own Docker container on AWS.

Services:
  1. API Gateway              (entry point for all requests)
  2. Auth Service             (login, register, JWT)
  3. Transaction Service      (CRUD for transactions)
  4. AI Scoring Service       (Gemini AI fraud scoring)
  5. Notification Service     (alerts, audit log)

Communication between services:
  Sync  (HTTP) : Frontend → API Gateway → Auth/Transaction Service
  Async (Queue): Transaction Service → SQS → AI Scoring Service
                 AI Scoring Service → SQS → Notification Service

This means:
  - When a transaction is created, Transaction Service puts a
    message on an AWS SQS queue
  - AI Scoring Service picks it up, scores it, updates the DB
  - Notification Service picks up the score result and logs it
  - Nothing blocks — everything is asynchronous and fast

2.5 DATABASE DESIGN (ONE MONGODB — THREE COLLECTIONS)
----------------------------------------------------

You only need ONE MongoDB Atlas free database.
One connection string. One free cluster.
Three collections inside it — one per service.

Each service only touches its own collection.
They never read each other's collection directly.
Communication happens only via SQS messages.

DATABASE NAME: fraudguard  (single database on Atlas)

  Collection 1: users        (used by Auth Service only)
  Collection 2: transactions (used by Transaction + Scoring Service)
  Collection 3: auditlogs    (used by Notification Service only)

All 4 services use the SAME MongoDB URI in their .env:
  MONGO_URI=mongodb+srv://youruser:yourpass@cluster.mongodb.net/fraudguard

Each service just uses mongoose.model() for its own collection only.
Auth Service never imports Transaction model. Transaction Service
never imports AuditLog model. This is called logical separation.

If a JP Morgan interviewer asks why one DB instead of three:
"I used a single MongoDB database with separate collections per
service to reduce infrastructure cost during development, while
keeping each service logically independent. In production I would
move each collection to its own database cluster for true isolation
and independent scaling."

COLLECTION SCHEMAS:

COLLECTION 1 — users (Auth Service)
  {
    _id          : ObjectId,
    name         : String (required),
    email        : String (unique, required),
    password     : String (bcrypt hashed),
    role         : String (enum: analyst | admin),
    isActive     : Boolean (default: true),
    lastLogin    : Date,
    createdAt    : Date,
    updatedAt    : Date
  }

COLLECTION 2 — transactions (Transaction + Scoring Service)
  {
    _id              : ObjectId,
    transactionId    : String (unique, required),
    amount           : Number (required),
    currency         : String (default: INR),
    merchantName     : String (required),
    merchantCategory : String (required),
    cardLastFour     : String,
    cardType         : String (enum: credit | debit),
    location         : { city: String, country: String, ipAddress: String },
    userId           : String,
    timestamp        : Date (required),
    status           : String (enum: pending|clean|suspicious|fraudulent),
    riskScore        : Number (0-100, default: 0),
    riskLevel        : String (enum: low|medium|high|critical),
    aiReasons        : [String],
    aiRecommendation : String (enum: approve|review|block),
    reviewedBy       : String (analyst userId as string),
    reviewedByName   : String,
    reviewedAt       : Date,
    reviewNote       : String,
    scoringStatus    : String (enum: queued|scoring|scored, default: queued),
    createdAt        : Date
  }
  Index: { transactionId: 1, timestamp: -1, status: 1, riskScore: -1 }

COLLECTION 3 — auditlogs (Notification Service)
  {
    _id            : ObjectId,
    transactionId  : String (required),
    analystId      : String,
    analystName    : String,
    action         : String (enum: approved|rejected|escalated|auto-flagged),
    note           : String,
    previousStatus : String,
    newStatus      : String,
    riskScore      : Number,
    timestamp      : Date (default: now),
    source         : String (enum: analyst | system)
  }

2.9 AWS DEPLOYMENT ARCHITECTURE
----------------------------------------------------

STEP BY STEP — WHAT GOES WHERE ON AWS

STEP 1: CONTAINER IMAGES → AWS ECR
  Each service gets its own ECR repository:
    fraudguard/auth-service
    fraudguard/transaction-service
    fraudguard/ai-scoring-service
    fraudguard/notification-service

  You push Docker images to ECR using GitHub Actions.

STEP 2: SERVICES RUN ON → AWS ECS (Fargate)
  ECS Fargate = serverless containers (no EC2 to manage)
  Each service = one ECS Task Definition + one ECS Service
  ECS Service keeps 1 container running at all times
  If container crashes, ECS automatically restarts it

STEP 3: REQUEST ROUTING → AWS Application Load Balancer
  One ALB with path-based routing:
    /auth/*     → forwards to Auth Service ECS tasks
    /transactions/* → forwards to Transaction Service ECS tasks
    /audit/*    → forwards to Notification Service ECS tasks

STEP 4: MESSAGE QUEUE → AWS SQS
  Two SQS queues in your AWS account:
    fraudguard-transaction-scoring-queue
    fraudguard-notification-queue
  AI Scoring Service polls queue every 5 seconds
  Notification Service polls queue every 5 seconds

STEP 5: SECRETS → AWS Secrets Manager
  Store sensitive values here (not in .env files on AWS):
    /fraudguard/mongo-uri
    /fraudguard/jwt-secret
    /fraudguard/claude-api-key
    /fraudguard/aws-sqs-region
  ECS tasks read secrets from Secrets Manager at startup

STEP 6: MONITORING → AWS CloudWatch
  All ECS container logs automatically go to CloudWatch
  Set up alerts for:
    - Service crashes (container health check fails)
    - Error rate above 5% in 5 minutes
    - AI scoring queue depth above 100 (backlog alert)

STEP 7: FRONTEND → AWS S3 + CloudFront
  Build React app: npm run build
  Upload /dist folder to S3 bucket
  CloudFront CDN sits in front of S3
  Users get the React app from nearest edge location
  Custom domain via Route 53 (optional)

STEP 8: CI/CD → GitHub Actions
  Every push to main branch:
    1. Run tests
    2. Build Docker image
    3. Push image to AWS ECR
    4. Update ECS service with new image
    5. ECS deploys new version with zero downtime

AWS FREE TIER USAGE (what you can use for free):
  ECS Fargate   : 750 hours/month free (first year)
  SQS           : 1 million messages/month free (always free)
  S3            : 5GB storage free (first year)
  CloudFront    : 1TB data transfer free (first year)
  CloudWatch    : 5GB log storage free (always free)
  ECR           : 500MB storage free (first year)
  Secrets Mgr   : $0.40 per secret per month (4 secrets = $1.60/month)

2.10 GITHUB ACTIONS CI/CD PIPELINE
----------------------------------------------------

File: .github/workflows/deploy-auth.yml

name: Deploy Auth Service

on:
  push:
    branches: [main]
    paths: ['services/auth-service/**']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ap-south-1

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v1

      - name: Build and push Docker image
        run: |
          docker build -t fraudguard/auth-service ./services/auth-service
          docker tag fraudguard/auth-service:latest \
            ${{ steps.login-ecr.outputs.registry }}/fraudguard/auth-service:latest
          docker push \
            ${{ steps.login-ecr.outputs.registry }}/fraudguard/auth-service:latest

      - name: Deploy to ECS
        run: |
          aws ecs update-service \
            --cluster fraudguard-cluster \
            --service auth-service \
            --force-new-deployment

Copy this file for each of the 4 services.
Change the path and service name for each one.

2.12 HOW TO EXPLAIN THIS IN JP MORGAN INTERVIEW
----------------------------------------------------

QUESTION: "Tell me about your architecture decisions."

ANSWER:
"I built FraudGuard as a microservices system on AWS. I split
the application into 4 services — Auth, Transaction, AI Scoring,
and Notification — each with its own MongoDB database and Docker
container. Services communicate asynchronously through AWS SQS
queues, which means creating a transaction is non-blocking — the
AI scoring happens in the background without making the user wait.
I deployed everything on AWS ECS Fargate with an Application Load
Balancer routing traffic, and set up a GitHub Actions CI/CD
pipeline that automatically builds Docker images, pushes them to
ECR, and deploys to ECS on every push to main. This architecture
mirrors how JP Morgan and other financial institutions structure
their payment processing systems."

QUESTION: "Why microservices instead of a monolith?"

ANSWER:
"Three reasons. First, each service can be scaled independently
— if AI scoring becomes a bottleneck, I can scale just that
container without touching the others. Second, a failure in
the notification service does not bring down the entire system.
Third, each service can be deployed independently — the auth
team does not need to coordinate with the transaction team for
deployments. These are exactly the reasons financial institutions
use microservices for their payment systems."

QUESTION: "Why SQS for communication?"

ANSWER:
"Because fraud scoring does not need to be synchronous. The
transaction is saved immediately and the user gets a response
right away. The AI scoring runs asynchronously in the background
via SQS. This means if the AI Scoring Service is temporarily
down, messages queue up and get processed when it comes back —
no transactions are lost. This is called message durability and
it is critical for financial systems."

File: /services/ai-scoring-service/src/services/aiScoringService.js

  const model = require('../config/geminiClient')

  async function scoreTransaction(transaction) {
    const prompt = `
      You are a bank fraud detection AI system.
      Analyze this transaction and return ONLY a JSON object.
      No explanation. No markdown. No code fences. Just raw JSON.

      Transaction:
      - ID: ${transaction.transactionId}
      - Amount: ${transaction.amount} INR
      - Merchant: ${transaction.merchantName}
      - Category: ${transaction.merchantCategory}
      - Location: ${transaction.location.city}, ${transaction.location.country}
      - Time: ${transaction.timestamp}
      - Card Type: ${transaction.cardType}
      - Card Last 4: ${transaction.cardLastFour}

      Return exactly this JSON:
      {
        "riskScore": <number 0-100>,
        "riskLevel": <"low" or "medium" or "high" or "critical">,
        "reasons": ["reason1", "reason2", "reason3"],
        "recommendation": <"approve" or "review" or "block">
      }

      Scoring rules:
      0-40   = low risk, normal transaction
      41-70  = medium risk, some flags, needs review
      71-90  = high risk, likely fraudulent
      91-100 = critical, block immediately

      Flag these patterns:
      - Late night time (11PM - 5AM) = suspicious
      - Amount above 50000 INR = suspicious
      - Electronics or jewelry category = higher risk
      - Unusual location = suspicious
    `

    try {
      const result = await model.generateContent(prompt)
      const text = result.response.text().trim()

      // Remove any markdown fences if Gemini adds them
      const clean = text.replace(/```json|```/g, '').trim()
      const parsed = JSON.parse(clean)

      return {
        riskScore: parsed.riskScore,
        riskLevel: parsed.riskLevel,
        aiReasons: parsed.reasons,
        aiRecommendation: parsed.recommendation
      }
    } catch (err) {
      console.error('Gemini scoring error:', err.message)
      // Return default safe score if AI fails — do not crash
      return {
        riskScore: 0,
        riskLevel: 'low',
        aiReasons: ['AI scoring unavailable'],
        aiRecommendation: 'review'
      }
    }
  }

  module.exports = { scoreTransaction }

4.4 SCORING WORKER — POLLS SQS AND SCORES
----------------------------------------------------

File: /services/ai-scoring-service/src/workers/scoringWorker.js

  const { SQSClient, ReceiveMessageCommand,
          DeleteMessageCommand } = require('@aws-sdk/client-sqs')
  const { scoreTransaction } = require('../services/aiScoringService')
  const Transaction = require('../models/Transaction')

  const sqs = new SQSClient({ region: process.env.AWS_REGION })
  const SCORING_QUEUE = process.env.SQS_SCORING_QUEUE_URL
  const NOTIFICATION_QUEUE = process.env.SQS_NOTIFICATION_QUEUE_URL

  async function pollQueue() {
    try {
      const command = new ReceiveMessageCommand({
        QueueUrl: SCORING_QUEUE,
        MaxNumberOfMessages: 5,
        WaitTimeSeconds: 10   // long polling — reduces cost
      })

      const response = await sqs.send(command)
      if (!response.Messages || response.Messages.length === 0) return

      for (const message of response.Messages) {
        const body = JSON.parse(message.Body)

        // Score the transaction with Gemini
        const score = await scoreTransaction(body)

        // Determine status from score
        let newStatus = 'clean'
        if (score.riskScore > 90) newStatus = 'fraudulent'
        else if (score.riskScore > 70) newStatus = 'suspicious'

        // Update transaction in MongoDB
        await Transaction.findOneAndUpdate(
          { transactionId: body.transactionId },
          {
            riskScore: score.riskScore,
            riskLevel: score.riskLevel,
            aiReasons: score.aiReasons,
            aiRecommendation: score.aiRecommendation,
            status: newStatus,
            scoringStatus: 'scored'
          }
        )

        // Send to notification queue
        await sqs.send(new SendMessageCommand({
          QueueUrl: NOTIFICATION_QUEUE,
          MessageBody: JSON.stringify({
            messageType: 'TRANSACTION_SCORED',
            transactionId: body.transactionId,
            riskScore: score.riskScore,
            riskLevel: score.riskLevel,
            newStatus,
            aiReasons: score.aiReasons,
            action: 'auto-flagged',
            source: 'system'
          })
        }))

        // Delete message from queue after processing
        await sqs.send(new DeleteMessageCommand({
          QueueUrl: SCORING_QUEUE,
          ReceiptHandle: message.ReceiptHandle
        }))

        console.log(`Scored ${body.transactionId}: ${score.riskScore} (${newStatus})`)
      }
    } catch (err) {
      console.error('Worker error:', err.message)
    }
  }

  // Poll every 5 seconds
  setInterval(pollQueue, 5000)
  console.log('AI Scoring Worker started — polling SQS every 5s')
