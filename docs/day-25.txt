DAY 25 - FULL FRONTEND INTEGRATION TEST EXPLANATION

This document breaks down the Day 25 integration test. It explains the flow of the entire application, what happens behind the scenes during each step of the walkthrough, and how the different microservices interact. Use this to prepare for interviews when asked about how the components of FraudGuard connect end-to-end.

--- 1. Register new admin account ---
- What happens: The user submits registration details on the frontend. The React app calls the `POST /auth/register` endpoint on the Auth Service.
- Behind the scenes: The Auth Service hashes the password using `bcrypt` and stores the new user document in the MongoDB database with the 'admin' role. A JWT token is generated and returned to the client, which stores it in local storage or a secure cookie.

--- 2. Login ---
- What happens: The user enters credentials. The React app calls the `POST /auth/login` endpoint on the Auth Service.
- Behind the scenes: The Auth Service verifies the email and password hash. It returns a new JWT token. Redux state is updated via `authSlice` to store user info, and the app routes to the protected `/dashboard` page using React Router.

--- 3. Go to Dashboard — verify charts load ---
- What happens: The Dashboard mounts and triggers `useEffect` hooks to fetch stats, trends, and category data.
- Behind the scenes: The React app calls the Transaction Service endpoints (like `GET /transactions/stats`, `GET /transactions/trends`). The Transaction Service queries MongoDB with aggregations (e.g., grouping by risk status or category) and returns the compiled metrics. Recharts renders the line, pie, and bar charts based on this data.

--- 4. Go to Transaction Feed ---
- What happens: The user navigates to the transactions page. A table component displays recent transactions.
- Behind the scenes: A `GET /transactions` call is made. The Transaction Service fetches paginated transaction data from MongoDB. The React TanStack table renders this data with formatting (e.g., custom RiskBadges).

--- 5. Generate 10 mock transactions ---
- What happens: The user clicks the "Simulate Razorpay Payment" button multiple times.
- Behind the scenes: The client calls the `POST /transactions/simulate` endpoint on the Transaction Service. The service creates dummy transaction records in MongoDB with a 'pending' status, and publishes message events to the SQS queue indicating new transactions need scoring.

--- 6. Wait 5-6 seconds for Gemini scoring ---
- What happens: The system asynchronously calculates fraud risk for the newly generated transactions.
- Behind the scenes: The AI Scoring Service (a background worker) polls the SQS queue, picks up the transaction messages, and calls the Gemini AI API with the transaction details. Gemini returns a risk score (0-100) and an explanation. 

--- 7. Refresh — check risk scores appeared ---
- What happens: The user refreshes the feed to view the scores.
- Behind the scenes: The AI Scoring Service has updated the transaction records in MongoDB with the calculated `riskScore`, `aiReasons`, and updated `status` (e.g., 'flagged' or 'clean'). The frontend re-fetches the list, showing updated RiskBadges and scores.

--- 8. Filter by suspicious ---
- What happens: The user uses the FilterBar to select the 'Suspicious' status.
- Behind the scenes: The frontend appends `?status=suspicious` (or similar) to the API request. The Transaction Service adds this filter to its MongoDB query and returns only the matching transactions.

--- 9. Click one to open detail page ---
- What happens: The user clicks the view icon for a specific transaction, navigating to `/transactions/:id`.
- Behind the scenes: The frontend gets the `id` from URL params using `useParams()` and makes a `GET /transactions/:id` request. The page displays the transaction details and the `RiskGauge` component.

--- 10. Read AI reasons on gauge ---
- What happens: The AI analysis card renders the risk score visually using `react-gauge-chart`.
- Behind the scenes: The frontend maps over the `aiReasons` array returned by Gemini and displays them as bullet points, explaining why the transaction was flagged (e.g., unusual location, high amount).

--- 11. Add note and approve ---
- What happens: The analyst types a justification note and clicks "Approve".
- Behind the scenes: The frontend calls the `PATCH /transactions/:id` endpoint on the Transaction Service with `{ status: 'approved', reviewNote: '...' }`. The service updates the DB and also sends an event to the Notification/Audit Service via SQS to log the analyst's action.

--- 12. Go to Review Queue — approve 2 more ---
- What happens: The user navigates to the queue, which only shows transactions that need review (high risk). They approve two more using inline action buttons.
- Behind the scenes: Same as step 11, but the frontend calls the API directly from the table row (via `ActionModal.jsx`) and refetches the queue list afterwards.

--- 13. Reject 1 with a note ---
- What happens: The user rejects a fraudulent transaction.
- Behind the scenes: The API receives a status of 'rejected'. The database is updated, and the Audit log records a rejection action. This affects overall dashboard stats for "Confirmed Fraud".

--- 14. Go to Audit Log — verify 4 entries ---
- What happens: The user navigates to the Audit Log page to see the history of analyst actions.
- Behind the scenes: The React app calls `GET /audit` on the Notification Service (port 3004). The service queries the `AuditLog` collection in MongoDB and returns the records, showing the analyst name, timestamp, action taken, and notes.

--- 15. Go to Dashboard — stats updated ---
- What happens: The user returns to the Dashboard.
- Behind the scenes: New `GET` requests fetch fresh aggregation data. The "Flagged", "Confirmed Fraud", and "Amount Saved" metrics reflect the recent approvals and rejections. 

--- 16. Export CSV — file downloads ---
- What happens: The user clicks the "Export CSV" button.
- Behind the scenes: The `GET /transactions/export` endpoint generates a CSV file on the fly (often using a library like `json2csv` or manual string building) and streams it back with the correct headers (`Content-Type: text/csv`, `Content-Disposition: attachment`). The browser handles the download.

--- 17. Go to Admin Panel — health shows 4 green dots ---
- What happens: The user opens the system health dashboard.
- Behind the scenes: The frontend makes asynchronous calls to the `/health` endpoints of all four microservices. Each service responds with a 200 OK status. The UI renders green dots to indicate the system is operational.

--- 18. Logout — goes to login page ---
- What happens: The user clicks logout.
- Behind the scenes: Redux dispatches the `logout` action, clearing the user state. The JWT token is removed from `localStorage`. The ProtectedRoute component detects no token and redirects the user back to the `/login` page.
