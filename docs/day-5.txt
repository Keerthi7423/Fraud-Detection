====================================================
DAY 5 — TRANSACTION SERVICE PART 1 (Setup + Model)
====================================================

In Day 5, we laid the foundation for the Transaction Service. This service is the heart of the FraudGuard system, responsible for handling all financial data and initiating the AI scoring process.

----------------------------------------------------
1. KEY IMPLEMENTATIONS
----------------------------------------------------

A. Transaction Service Initialization
   - Created a new microservice under `services/transaction-service`.
   - Installed essential dependencies: `express`, `mongoose`, `dotenv`, `jsonwebtoken`, `cors`, `morgan`, `helmet`, and `@aws-sdk/client-sqs`.
   - Set up the server on Port 3002 to differentiate it from the Auth Service (Port 3001).

B. Database Configuration (config/db.js)
   - Responsibility: Establishes a connection to MongoDB Atlas.
   - Note: Both Auth and Transaction services connect to the SAME MongoDB cluster but manage different collections. This is a "Logical Separation" strategy.

C. Transaction Model (models/Transaction.js)
   - Responsibility: Defines the structure of a transaction in the database.
   - Key Fields:
     - `transactionId`: Unique identifier for each transaction.
     - `amount`, `currency`, `merchantName`, `merchantCategory`: Core transaction data.
     - `status`: Tracks the lifecycle (pending, clean, suspicious, fraudulent).
     - `riskScore` & `riskLevel`: Stores the results from the AI Scoring Service.
     - `scoringStatus`: Tracks if the AI has finished processing (queued, scoring, scored).
   - Optimization: Added a compound index `{ transactionId: 1, timestamp: -1, status: 1, riskScore: -1 }` to ensure lightning-fast queries even with millions of records.

D. Shared Authentication Middleware (middleware/authMiddleware.js)
   - Responsibility: Reused the JWT logic from the Auth Service.
   - Concept: Since both services use the same `JWT_SECRET`, a token generated by the Auth Service is valid for the Transaction Service. This allows for seamless cross-service communication.

----------------------------------------------------
2. INTERVIEW PREPARATION (JP MORGAN / TIER-1 FINTECH)
----------------------------------------------------

QUESTION 1: "Why did you split Transactions and Auth into separate services?"
ANSWER: 
"In a high-scale system like JP Morgan's, the volume of transactions is massive compared to the number of logins. By splitting them, we can scale the Transaction Service independently (e.g., running 10 instances) while keeping the Auth Service small. It also ensures that if the Auth Service goes down, the Transaction Service can still process existing sessions."

QUESTION 2: "What is a Compound Index and why did you use it for Transactions?"
ANSWER:
"A compound index is an index on multiple fields. I used it on `{ transactionId, timestamp, status, riskScore }` because these are the most common filters used in the dashboard. For example, 'Find all suspicious transactions from yesterday with high risk scores.' Without this index, MongoDB would have to scan every single document, which is too slow for financial systems."

QUESTION 3: "How do your microservices share authentication?"
ANSWER:
"They use a Shared Secret approach. Both the Auth Service (which signs the token) and the Transaction Service (which verifies it) have access to the same `JWT_SECRET` in their environment variables. This allows the Transaction Service to verify user identity without making a slow network call to the Auth Service for every request."

QUESTION 4: "Why use a separate collection for Transactions instead of a separate Database?"
ANSWER:
"I used logical separation (separate collections) within one MongoDB Atlas cluster to keep infrastructure costs low during development. However, the code is designed such that we can point each service to a completely different database URI in the future without changing a single line of logic. This is the 'Database-per-Service' pattern."
