FRAUDGUARD — DAY 1 TECHNICAL DEEP DIVE & INTERVIEW PREP
====================================================

Congratulations on completing Day 1! This document is designed to help you explain the technical decisions made today during an interview at JP Morgan or any Tier-1 fintech company.

----------------------------------------------------
1. ARCHITECTURE DECISIONS: WHY MICROSERVICES?
----------------------------------------------------

Interview Question: "Why did you choose a microservices architecture for this project instead of a simple monolith?"

Your Answer:
"I chose microservices because they align with how large-scale financial systems operate. In FraudGuard, we have 5 independent services:
- Auth
- Transaction
- AI Scoring
- Notification
- API Gateway

Key Benefits:
- Scalability: If AI scoring becomes a bottleneck (due to high transaction volume), I can scale just the AI Scoring Service without wasting resources on the Auth or Notification services.
- Fault Tolerance: If the Notification Service fails, the core system (Auth and Transactions) continues to work. Transactions are still scored and recorded.
- Decoupling: Different services can use different tech stacks if needed (e.g., Python for AI, Node.js for Auth).

----------------------------------------------------
2. DATA ISOLATION & THE "ONE DB" STRATEGY
----------------------------------------------------

Interview Question: "You are using a single MongoDB database. Isn't that a 'Distributed Monolith'?"

Your Answer:
"For this phase, I am using logical isolation. Each service only interacts with its own collection (e.g., Auth Service only touches the 'users' collection). They never share models or read each other's data directly. This ensures that when we scale to production, we can easily split these collections into physically separate database clusters without changing the business logic. It's a cost-effective way to develop while maintaining strict architectural boundaries."

----------------------------------------------------
3. SYNC VS ASYNC COMMUNICATION
----------------------------------------------------

Interview Question: "How do your services talk to each other?"

Your Answer:
"We use two patterns:
1. Sync (HTTP): Frontend talks to the API Gateway, which forwards requests to Auth or Transaction services.
2. Async (SQS): When a transaction is created, the Transaction Service publishes a message to AWS SQS. The AI Scoring Service picks it up whenever it's ready. This is 'Event-Driven Architecture' and it ensures that the user doesn't have to wait for the AI to process before getting a 'Success' response."

----------------------------------------------------
4. TECH STACK CHOICES
----------------------------------------------------

Interview Question: "Why Express.js and the specific middlewares you chose (Helmet, Morgan, Cors)?"

Your Answer:
"Express.js is lightweight and highly performant for microservices.
- Helmet: Adds security headers to prevent common web vulnerabilities like XSS and clickjacking.
- Morgan: Provides standard request logging for observability.
- CORS: Manages Cross-Origin Resource Sharing, essential when the frontend and backend are on different domains.
- Joi/Joi: For schema validation. In a microservices environment, ensuring that input data is valid before it travels through the system is critical to prevent cascading failures."

----------------------------------------------------
5. THE IMPORTANCE OF THE HEALTH CHECK
----------------------------------------------------

Interview Question: "What is the purpose of the /health endpoint you created?"

Your Answer:
"The /health endpoint is critical for cloud orchestration. Services like AWS ECS or Kubernetes use this 'Liveness Probe' to monitor the health of the container. If the endpoint stops responding with a 200 OK, the orchestrator automatically kills and restarts the container, ensuring high availability."
