DAY-7: TRANSACTION SERVICE PART 3 (CRUD CONTROLLER & ANALYTICS)
============================================================

Today's focus was on completing the core business logic of the Transaction Service. This involved implementing CRUD (Create, Read, Update, Delete) operations, advanced filtering, dashboard statistics, and fraud analytics.

1. TECHNICAL OVERVIEW: TRANSACTION CONTROLLER
----------------------------------------------
The `transactionController.js` is the heart of the Transaction Service. It handles all incoming requests related to payment transactions and fraud review.

A. CRUD OPERATIONS:
- getAllTransactions: Implements a multi-filter search system. Analysts can filter by status, category, amount range, date range, and a general search term (for Transaction ID or Merchant Name).
- getOneTransaction: Retrieves a specific transaction using its unique `transactionId`.
- createTransaction: The entry point for new data. If no body is provided, it uses `generateMockTransaction()` to simulate a real payment event. This is crucial for demonstrating the system's capabilities during interviews.
- updateTransactionStatus: Implements the "Analyst Review" workflow. It maps human-friendly actions (approved, rejected, escalated) to system statuses (clean, fraudulent, suspicious).

B. ASYNC COMMUNICATION (SQS):
- When a transaction is created, `sendToScoringQueue` is called. This is a "Fire and Forget" operation (non-blocking).
- This mirrors high-scale systems where the main transaction flow shouldn't wait for background tasks like AI scoring or risk assessment.

2. ANALYTICS & AGGREGATIONS (MONGODB AGGREGATION PIPELINE)
---------------------------------------------------------
For the dashboard to be useful, it needs data-dense insights. We implemented three key analytical endpoints using MongoDB's Aggregation Framework:

A. getDashboardStats:
- Calculates real-time stats for "Today" (from midnight onwards).
- Uses `$cond` inside a `$group` stage to count flagged/confirmed fraud and sum the "saved" amount (amount of transactions marked as fraudulent).

B. getFraudTrends:
- Aggregates the count of suspicious/fraudulent transactions over the last 7 days.
- Uses `$dateToString` to group by day and `$sort` to ensure the timeline is chronological.

C. getFraudByCategory & getFraudByHour:
- Breakdown of fraud by merchant category (e.g., electronics, food) and by the hour of the day.
- Helping analysts identify high-risk time windows or vulnerable sectors.

3. INTERVIEW PREPARATION - KEY TALKING POINTS
---------------------------------------------

Q: "How did you handle the high volume of transactions in your design?"
A: "I used an asynchronous, non-blocking architecture. When a transaction is created, it's saved to MongoDB immediately, and a message is sent to an AWS SQS queue for AI scoring. The controller doesn't 'await' the AI response, ensuring the user (or payment gateway) gets an immediate 201 Created response. This is how Tier-1 fintechs handle millions of TPS."

Q: "Why did you use MongoDB Aggregation for the dashboard instead of simple finds?"
A: "Aggregation is significantly more efficient for analytical queries. Instead of fetching thousands of documents and calculating totals in Node.js (which consumes memory and CPU), I offload the computation to the database engine. Using stages like $match, $group, and $project allows the database to return only the final results, reducing network overhead."

Q: "How does the analyst review workflow work?"
A: "I implemented a status mapping logic. When an analyst reviews a transaction, they choose an action like 'rejected'. The controller maps this to a system status of 'fraudulent', records who reviewed it, when they did it, and requires a mandatory review note of at least 10 characters for auditability."

Q: "How do you handle security in these routes?"
A: "All routes are protected by a JWT authMiddleware. Additionally, sensitive operations like updating a transaction status are further protected by a role-based authorization middleware (authorize('admin', 'analyst')), ensuring only authorized personnel can flag or clear transactions."
