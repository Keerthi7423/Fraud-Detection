====================================================
DAY 6 — TRANSACTION SERVICE PART 2 (MOCK GENERATOR + SQS)
====================================================

In Day 6, we focused on two critical components of the Transaction Service:
1. Mock Transaction Generation: To facilitate testing without needing real transaction data.
2. SQS Integration: To enable asynchronous communication between microservices (Event-Driven Architecture).

----------------------------------------------------
1. MOCK TRANSACTION GENERATOR (src/utils/generateMockTransaction.js)
----------------------------------------------------
The purpose of this utility is to generate realistic but fake transaction data. This is essential for:
- Testing the frontend without a real payment gateway.
- Stress testing the AI Scoring Service.
- Verifying the dashboard visualizations.

KEY COMPONENTS:
- Random Data Sets: Lists of merchants (Amazon, Zomato, etc.), categories (food, electronics), and cities (Mumbai, Delhi) to provide variety.
- Transaction ID: Uses 'TXN-' prefix combined with the last 5 digits of Date.now() to ensure uniqueness during rapid testing.
- Field Schema: Matches the MongoDB 'Transaction' model exactly, ensuring data integrity when saved to the database.

INTERVIEW EXPLANATION:
"I implemented a mock data generator to streamline the development and testing process. It generates randomized fields like transactionId, amount, and merchant info, allowing us to simulate real-world traffic patterns and verify that our data pipelines (like SQS and AI Scoring) handle diverse inputs correctly."

----------------------------------------------------
2. SQS CLIENT CONFIGURATION (src/config/sqsClient.js)
----------------------------------------------------
We use the AWS SDK v3 to interact with Amazon SQS (Simple Queue Service).

WHY AWS SDK v3?
- Modular architecture: We only import the SQS client (@aws-sdk/client-sqs), which reduces bundle size compared to v2.
- Promise-based: Cleaner code using async/await.

LOGIC:
- It initializes the SQSClient with the region specified in the .env file (defaulting to 'ap-south-1').
- It uses credentials (accessKeyId and secretAccessKey) from environment variables.

----------------------------------------------------
3. ASYNCHRONOUS QUEUE SERVICE (src/services/queueService.js)
----------------------------------------------------
This is the "Producer" in our message-driven architecture.

LOGIC:
- sendToScoringQueue(transaction): This function takes a transaction object and prepares a message for SQS.
- DEV Mode Handling: In development (NODE_ENV=development), it logs the message to the console instead of sending it to real AWS. This prevents AWS costs during early coding and allows developers to work without an internet connection to AWS.
- Message Format: The message body is a JSON string containing the 'messageType' (SCORE_TRANSACTION) and the relevant transaction details.
- Error Handling: Wrapped in a try-catch block to ensure that if SQS fails (e.g., network issues), the main transaction creation flow is NOT interrupted. This is the "Fail-Safe" nature of microservices.

INTERVIEW EXPLANATION:
"I implemented an asynchronous messaging pattern using AWS SQS. When a transaction is created, the Transaction Service acts as a producer, sending a message to a scoring queue. I designed this as a non-blocking operation (fire-and-forget), so the user doesn't have to wait for the AI to analyze the transaction. In development, I added a mock layer to log these messages to the console, ensuring we can test the logic without incurring cloud costs."

----------------------------------------------------
SUMMARY OF ARCHITECTURE BENEFITS
----------------------------------------------------
- Scalability: The AI Scoring service can be scaled independently if the volume of transactions increases.
- Reliability: If the AI Scoring service is down, messages stay in the SQS queue and are processed when the service comes back online (Message Durability).
- Performance: The Transaction Service returns a response to the user immediately after saving to DB, while the 'heavy' AI scoring happens in the background.
