DAY 21: AUDIT LOG PAGE - TECHNICAL IMPLEMENTATION & INTERVIEW PREPARATION
=============================================================================

1. OVERVIEW OF DAY 21
---------------------
The primary objective of Day 21 was to implement the "Audit Log" page for the FraudGuard platform. The Audit Log tracks and displays all actions performed by analysts or the system, ensuring accountability, system integrity, and compliance with enterprise standards (common in systems built at JP Morgan or other tier-1 financial institutions).

2. COMPONENTS BUILT & MODIFIED
------------------------------

A. `client/src/services/auditService.js`
----------------------------------------
- What it is: A dedicated Axios service layer specifically for interacting with the Notification Service's audit endpoints on port 3004.
- Why we need it: In microservices, frontend components shouldn't directly use fetch or hardcode URLs. By decoupling the API calls into a service file, we can handle the logic centrally, making components cleaner and making it easy to swap endpoints when deploying to AWS.
- Key Functions:
  * `getAuditLogs(filters)`: Takes an object with search parameters (analystName, action, startDate, endDate) and triggers a GET request to `/audit`.

B. `client/src/pages/AuditLog.jsx`
----------------------------------
- What it is: The main user interface for the Audit Log.
- Key Implementation Details:
  1. Role-Based Access Control (RBAC):
     The component checks if the logged-in user is an admin using `useSelector((state) => state.auth)`. If they are not an admin (`user.role !== 'admin'`), they are automatically redirected to the dashboard using React Router's `<Navigate>` component.
  2. Data Fetching & State:
     The component uses React's `useEffect` to trigger data fetching upon mounting. It uses local component state to store logs, loading status, and the current filter values.
  3. Inline Filters:
     Implemented UI inputs for:
       - Analyst Name (Text Input)
       - Action Type (Dropdown/Select for Approved, Rejected, Escalated, Auto-Flagged)
       - Date Range (using `react-datepicker` for start and end dates)
  4. Visual Indicators (Risk/Action Colors):
     To provide at-a-glance meaning, actions are color-coded based on the PRD specification:
       - Approved: Green (#22C55E)
       - Rejected: Red (#EF4444)
       - Escalated: Amber (#F59E0B)
       - Auto-Flagged: Blue (#3B82F6)
  5. UI Polish:
     - Includes a `LoadingSkeleton` during API calls to improve perceived performance.
     - Includes an `EmptyState` component when no logs are available.

C. `services/notification-service/src/controllers/auditController.js`
---------------------------------------------------------------------
- What we changed: Updated the `getAllAuditLogs` function to support query parameters.
- Why we needed it: The AuditLog frontend sends filtering criteria (`?analystName=...&action=...`). The MongoDB query in the backend needed to be dynamically built to support these filters.
- Technical Details:
  - Used regex (`$regex: analystName, $options: 'i'`) for case-insensitive partial matching on the analyst's name.
  - Used `$gte` (greater than or equal) and `$lte` (less than or equal) for filtering timestamps based on start and end dates.

3. INTERVIEW PREPARATION (HOW TO EXPLAIN DAY 21)
------------------------------------------------

Q: Why do you need an Audit Log in a system like this?
A: In financial and tier-1 systems (like JP Morgan's), every action taken by an employee or automated system must be fully traceable for compliance and security reasons. An audit log provides an immutable record of "who did what, and when", which is essential for investigating both fraudulent activities and internal mistakes.

Q: How did you implement filtering in the frontend and backend?
A: In the frontend, I used React state to manage filter inputs (text, dropdowns, and date pickers). When applied, I passed these state variables as query parameters through Axios. On the backend (Node.js/Express), I dynamically constructed a MongoDB query object based on `req.query`, using operators like `$regex` for text search and `$gte`/`$lte` for date ranges, ensuring the database does the heavy lifting rather than filtering in the client.

Q: How did you handle authorization (RBAC) for this page?
A: I implemented Role-Based Access Control on both sides. On the frontend, the `AuditLog` component checks the Redux store for the user's role and immediately redirects non-admins. On the backend, we would use middleware to decode the JWT and verify the role before returning any data.

Q: How does the data get into the Audit Log in the first place?
A: It relies on our asynchronous messaging architecture. When a transaction is reviewed in the Transaction Service, or auto-flagged by the AI Scoring Service, they publish a message to the AWS SQS Notification Queue. The Notification Service consumes this message in the background and saves it to the auditlogs collection in MongoDB. This prevents the primary services from being blocked by logging overhead.
