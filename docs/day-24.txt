## SECTION 1: ARCHITECTURAL OVERVIEW & REFACTORING LOG

### 1.1 Microservices Health Dashboard
*   **The Problem:** In a distributed microservices setup (Auth, Transactions, AI Scoring, Notifications), failure of a single service can silently break user workflows without visual indicators. Administrators need a real-time health dashboard to pinpoint which container is down.
*   **The Solution:**
    *   Designed a visual diagnostic panel in `AdminPanel.jsx` that queries the `/health` endpoint of all 4 independent microservices.
    *   Implemented automated polling that re-queries service nodes every 30 seconds to maintain high-fidelity monitoring.
    *   Tracks network latency in milliseconds by recording timestamps before and after the HTTP call.
    *   Provides instant visual feedback using color-coded status badges and pulsing indicator lights (Green = Online, Red = Offline).

### 1.2 Administrative Access Control & User Management
*   **The Problem:** System security requires deactivating compromised or inactive accounts immediately. However, there was no centralized admin mechanism to toggle user statuses, and deactivated users could still log in using existing passwords.
*   **The Solution:**
    *   **Backend API Endpoints:** Built a secure `GET /auth/users` router to list all users, and a `PATCH /auth/users/:id/toggle` controller to invert the `isActive` state of any account.
    *   **Login Guard:** Refactored the `POST /auth/login` endpoint in the Auth Service. If a user tries to authenticate but their `isActive` property is set to `false`, the controller blocks the request with a `403 Forbidden` response and does not issue a JWT.
    *   **UI Implementation:** Created a responsive admin table listing all registered analysts and admins. Admin operators can toggle active/inactive states with a click, supported by modal confirmation overlays and self-deactivation warning guards.

### 1.3 Asynchronous Queue Counter (Redux Badge)
*   **The Problem:** Analysts working in different screens (e.g., dashboard, logs) are unaware of incoming suspicious transactions unless they manually refresh the queue, resulting in delayed reviews.
*   **The Solution:**
    *   Added a `queueCount` field and `setQueueCount` action to the Redux `authSlice` to make queue stats globally accessible.
    *   Refactored the global layout shell (`Sidebar.jsx`) to run a background hook polling the transaction service (`GET /transactions/queue`) every 30 seconds.
    *   Calculates the count of pending/suspicious records and updates the Redux store, causing the sidebar badge to render a red pulsing number if cases are waiting for review.

### TOPIC 1: DISTRIBUTED HEALTH MONITORING & NETWORK DIAGNOSTICS
--------------------------------------------------------------------------------
Q1: How did you implement health checking across different microservices, and how do you prevent blocking the main thread when checking them concurrently?
--------------------------------------------------------------------------------
A: To check service availability without blocking execution, I used Javascript's asynchronous concurrency model. In the frontend component (`AdminPanel.jsx`), I initiated a parallel HTTP check across all services:

```javascript
const checkHealth = async () => {
  setLoading(true);
  const updatedServices = await Promise.all(
    services.map(async (service) => {
      try {
        const start = Date.now();
        const response = await axios.get(`${service.url}/health`, { timeout: 5000 });
        const latency = Date.now() - start;
        return { 
          ...service, 
          status: 'online', 
          health: { 
            latency, 
            timestamp: new Date().toLocaleTimeString(),
            version: response.data.version || '1.0.0'
          } 
        };
      } catch (err) {
        return { ...service, status: 'offline', health: null };
      }
    })
  );
  setServices(updatedServices);
  setLoading(false);
};
```
**Key Concepts Under the Hood:**
1.  **`Promise.all` Parallelism:** Instead of awaiting each HTTP request sequentially (which would block the UI and take up to 20 seconds if all services timed out), `Promise.all` fires all HTTP requests concurrently. The browser handles these requests on separate network sockets, returning the results together.
2.  **Request Timeout Guard:** I set a strict `{ timeout: 5000 }` on axios. If a service is completely unresponsive or a firewall is blocking the traffic, the request fails fast rather than keeping the TCP socket open indefinitely.
3.  **Latency Measurement:** By subtracting the initiation epoch (`Date.now()`) from the completion epoch inside the resolved promise, we calculate real-world network round-trip time (RTT). This serves as a vital diagnostic metric for detecting traffic bottlenecks or database degradation.

Q2: What is the purpose of a `/health` endpoint? What is the difference between a "shallow" health check and a "deep" health check?
--------------------------------------------------------------------------------
A: This is a classic DevOps and system design question.
*   **Shallow Health Check:** 
    *   **Definition:** The endpoint responds with `200 OK` as long as the HTTP server process (e.g., Express) is running and listening on the port.
    *   **Usage:** Used by container orchestrators (like AWS ECS or Kubernetes) for rapid container liveness probes (checking if the container should be restarted).
*   **Deep Health Check:**
    *   **Definition:** The endpoint performs a connection test on all critical internal dependencies—like pinging the MongoDB cluster, checking SQS queue reachability, and calling external APIs—before returning a status.
    *   **Usage:** Used for readiness probes (checking if the container is fully prepared to handle client traffic) and administration panels. If database pool connections are exhausted, a deep check returns `503 Service Unavailable`, taking the instance out of the load balancer.


### TOPIC 2: ROLE-BASED ACCESS CONTROL & LOGIN FLOW SECURITY
--------------------------------------------------------------------------------
Q3: How did you implement administrative deactivation of users? Explain how the request is authorized on the backend.
--------------------------------------------------------------------------------
A: Account deactivation requires role-based access control (RBAC). Both listing users and toggling status must be restricted to users with the `admin` role. I implemented this security layer on the Express backend using middleware checks:

1.  **Authentication Middleware (`protect`):** Verifies the incoming authorization header contains a valid JWT. If valid, the token is decoded, and the user's ID and role payload are attached to the request object (`req.user = decoded`).
2.  **Authorization Middleware (`authorize`):** Inspects the attached `req.user.role`. If the role is not included in the allowed roles array, it blocks execution and returns a `403 Forbidden` error.

```javascript
// middleware/authMiddleware.js
exports.authorize = (...roles) => {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({
        success: false,
        error: `User role ${req.user.role} is not authorized to access this route`,
      });
    }
    next();
  };
};

// routes/authRoutes.js
router.get('/users', protect, authorize('admin'), getUsers);
router.patch('/users/:id/toggle', protect, authorize('admin'), toggleUserStatus);
```

On the database level, the toggle controller retrieves the user document by ID, inverts the boolean value of the `isActive` property, saves it back to the database, and returns the modified user:

```javascript
// controllers/authController.js
exports.toggleUserStatus = async (req, res, next) => {
  try {
    const user = await User.findById(req.params.id);
    if (!user) {
      return res.status(404).json({ success: false, error: 'User not found' });
    }
    user.isActive = !user.isActive;
    await user.save();
    res.status(200).json({ success: true, data: user });
  } catch (err) {
    res.status(400).json({ success: false, error: err.message });
  }
};
```

Q4: What happens to a user who is currently logged in when their account is deactivated? How would you handle instant deactivation in a production system?
--------------------------------------------------------------------------------
A: This is an advanced security concept. 
*   **Current Setup Behavior:** If an analyst is active on the dashboard when deactivated, they will remain authenticated on their current session until their JWT expires (e.g., after 30 days) because JWTs are stateless. However, if they log out or their token expires, they cannot log back in, because the login handler checks the database `isActive` status:
    ```javascript
    if (!user.isActive) {
      return res.status(403).json({
        success: false,
        error: 'Your account has been deactivated. Please contact an administrator.',
      });
    }
    ```
*   **Production Immediate Deactivation Options:** If a company requires immediate session invalidation, we can implement:
    1.  **Token Blacklisting (Redis Cache):** Store deactivated user IDs in a fast-access Redis cache. The auth middleware on every API gateway checks if the JWT's `userId` is in the blacklist. If present, it denies access immediately.
    2.  **Short-Lived Access Tokens + Refresh Tokens:** Issue short-lived access tokens (e.g., 15 minutes) and a longer-lived refresh token. Every 15 minutes, the client must send the refresh token to the auth service. During refresh, the database is queried to check if `isActive` is false. If deactivated, the refresh request is denied, forcing a client logout.
    3.  **WebSocket / Event-Driven Eviction:** Emit a "deactivated" event over a WebSocket or server-sent events (SSE) channel. The client intercepts the event, clears the localStorage credentials, and redirects to the login screen.


### TOPIC 3: REAL-TIME NOTIFICATION COUNTERS & STATE MANAGEMENT
--------------------------------------------------------------------------------
Q5: Why did you choose to store the queue count in Redux instead of local component state?
--------------------------------------------------------------------------------
A: Using Redux allows us to decouple the fetching of data from where it is displayed:
1.  **Single Source of Truth:** Storing the `queueCount` in the Redux store (`authSlice`) allows multiple independent components (such as the `Sidebar` navigation link, the `Navbar` alerts dropdown, and the `ReviewQueue` header itself) to access the exact same state without prop-drilling.
2.  **State Persistence and Sharing:** If the count were restricted to `Sidebar.jsx` local state, transitioning pages would require complex callback functions to share that state with the main page views. With Redux, any component can dispatch `setQueueCount(count)` to update all subscribing elements instantly.
3.  **UI Performance:** React Redux handles selective re-rendering. Components that don't depend on the count will skip re-render cycles, optimizing execution speeds.

--------------------------------------------------------------------------------
Q6: What are the trade-offs of polling the microservices every 30 seconds for the queue count vs using WebSockets?
--------------------------------------------------------------------------------
A: Choosing the right communication channel is a primary system design topic.
*   **HTTP Short Polling (Our Current Approach):**
    *   **Pros:** Extremely simple to implement. Standard HTTP stateless calls are compatible with basic REST APIs and require no persistent server-side connection resources.
    *   **Cons:** Overhead and latency. Every 30 seconds, a full HTTP handshake is executed. If there are 1,000 active dashboard sessions, the backend will receive 2,000 requests per minute just to check the count, which can degrade database read performance. Also, there is a maximum of 30 seconds delay before an analyst sees a new suspicious transaction.
*   **WebSockets (Bi-directional Persistent Connection):**
    *   **Pros:** Instantaneous real-time notifications. As soon as a transaction's AI score is flagged, the transaction service pushes the notification. Zero polling overhead.
    *   **Cons:** State maintenance. Servers must keep an open TCP connection for every connected client. If there are tens of thousands of active users, this exhausts file descriptors and socket limits on web servers, requiring load balancing solutions (like Redis Adapter or AWS API Gateway WebSockets).
*   **Server-Sent Events (SSE - Uni-directional Streaming):**
    *   **Pros:** Lightweight compared to WebSockets, runs over standard HTTP, and has automatic reconnection support. Great for dashboards where data only flows from the server to the client.
